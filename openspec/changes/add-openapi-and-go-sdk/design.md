## Context

`ldap-service` exposes five HTTP endpoints today:

| Method | Path | Purpose |
|---|---|---|
| GET | `/healthz` | Liveness |
| GET | `/readyz` | Readiness (LDAP pools reachable) |
| POST | `/api/v1/ldap/lookup` | Single-account lookup |
| POST | `/api/v1/ldap/lookup/batch` | Batch lookup |
| POST | `/api/v1/ldap/authenticate` | Username/password auth |

Domain types live in `internal/domain/` (e.g. `Account`, `Problem`); handler logic lives in `internal/handler/`. Consumers (PHP monolith, upcoming `mfa-service`, and developer agents) must reverse-engineer the contract today. As the consumer count grows, the cost of N×teams hand-rolling clients compounds.

This change introduces a **machine-readable contract (OpenAPI 3.1)** as the single source of truth, a **generated Go SDK** for human and agent code, and an **`AGENTS.md`** as the cross-agent integration pointer. Per the proposal's resolved open questions: SDK lives at `pkg/ldapclient` in this repo; the spec is hand-authored; initial version is `0.1.0`.

## Goals / Non-Goals

**Goals:**

- Every public endpoint, request/response schema, security scheme, and error shape is described in `api/openapi.yaml`.
- A `pkg/ldapclient` Go SDK, regenerable from the spec, gives consumers a typed, tested client with idiomatic error handling.
- A single `AGENTS.md` file is the agent integration vector — Claude, Copilot, Cursor, and future agents all read it.
- CI enforces (a) spec lint passes and (b) committed SDK is up-to-date with the spec.
- Documentation-only: zero behavioral change to handlers.

**Non-Goals:**

- Splitting the SDK into a separate `ldap-client-go` repo.
- Generating the spec from handler annotations (`swag`, `kin-openapi`). Hand-authored.
- Multi-language SDKs (PHP, TypeScript). Add when a non-Go consumer materializes.
- Hosting Swagger UI / Redoc. Static GitHub Pages can follow later.
- Changing handler request/response shapes. If spec disagrees with handler, the **handler is correct** and the spec is fixed in this same change.
- Per-agent skill files (`.claude/skills/ldap-client/`, `.cursorrules`, etc.).

## Decisions

### D1. OpenAPI 3.1, not 3.0

**Choice**: `openapi: 3.1.0` in `api/openapi.yaml`.

**Why**: 3.1 aligns with JSON Schema 2020-12 (proper `null` handling, `examples` plural, `type: ["string","null"]` instead of `nullable: true`). `oapi-codegen v2` fully supports 3.1.

**Alternatives considered**: 3.0 has wider tooling support, but every modern lint/codegen tool we'd pick handles 3.1 in 2026.

### D2. Hand-authored single-file spec

**Choice**: One file `api/openapi.yaml`. No `$ref`-split into multiple files for MVP.

**Why**: 5 endpoints. Splitting adds path-resolution overhead in tooling and reviewer cognitive load with no payoff at this size. We can split later if the file exceeds ~800 lines.

**Alternatives considered**:

- *Generated from `swag` annotations*: tighter sync but requires annotating handlers (touches `internal/`); we rejected handler changes in the proposal.
- *Multi-file `$ref`*: postponed until size justifies it.

### D3. Generator: `oapi-codegen v2`

**Choice**: `github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen`, pinned via `tools.go` and a `tools` Go module.

**Why**: De facto standard Go OpenAPI generator. Idiomatic output (Go interfaces, named structs, `*http.Client` injection), no runtime dep on the generator itself, supports OpenAPI 3.1.

**Alternatives considered**:

- *`openapi-generator-cli` (Java-based)*: heavier, more language-friendly but generates non-idiomatic Go.
- *`go-swagger`*: 3.0 only, on a slow release cadence in 2026.

### D4. SDK package layout

**Choice**:

```
pkg/ldapclient/
  client.go         hand-authored: Client struct, New(), functional options
  errors.go         hand-authored: sentinel errors, ProblemError type
  doc.go            hand-authored: package doc, runnable Examples
  generated.go      auto-generated by oapi-codegen (types + raw client)
  client_test.go    hand-authored: round-trip tests vs httptest.Server
```

**Why**: Hand-authored `Client` wraps the generator's raw client to surface a smaller, opinionated public API and centralize error mapping. Splits "stable hand-written surface" from "regen-on-spec-change generated surface" at the file level.

**Alternatives considered**:

- *Use the generator's emitted client directly*: leaks codegen quirks (every endpoint returns a generic `*http.Response`), forces every consumer to write the same error-parsing boilerplate.

### D5. Constructor: `New(baseURL, apiKey string, opts ...Option) (*Client, error)`

**Choice**: Required positional args for the two values you cannot omit. Functional options for everything else: `WithHTTPClient(*http.Client)`, `WithUserAgent(string)`, `WithTimeout(time.Duration)`.

**Why**: Standard Go idiom (`grpc.Dial`, `http.NewRequestWithContext` style). Required things are required at the type level; everything optional is opt-in.

**Alternatives considered**:

- *Config struct*: more verbose at the call site for the common case; doesn't enforce required values.

### D6. Error mapping

**Choice**: For every documented non-2xx status, the SDK returns an error that:

- Wraps a `*ProblemError` carrying the parsed RFC 7807 fields (`type`, `title`, `status`, `detail`, `instance`, `request_id`).
- Matches a sentinel via `errors.Is` — `ErrUnauthorized`, `ErrTooManyRequests`, `ErrAccountNotFound`, `ErrBadRequest`, `ErrInternal`.
- Preserves the underlying transport error via `errors.Unwrap` for IO failures.

**Why**: Lets consumers write `if errors.Is(err, ldapclient.ErrTooManyRequests) { backoff() }` without sniffing status codes. Keeps the typed problem detail accessible via `errors.As(err, &pe)` for diagnostic logging.

**Alternatives considered**:

- *Return `(*Response, error)` and let the caller branch on `Response.StatusCode`*: pushes the error taxonomy onto every caller. Loses the value of having an SDK at all.

### D7. CI drift detection

**Choice**: `go generate ./pkg/ldapclient/...` regenerates `generated.go`. CI runs `go generate` then `git diff --exit-code pkg/ldapclient/`; non-empty diff fails the build.

**Why**: The committed SDK and the spec must stay in lockstep. Catching drift in CI is cheaper than at consumer integration time.

**Alternatives considered**:

- *Generate at build time, do not commit*: forces every consumer (including non-CI environments) to have the codegen toolchain. Worse DX.

### D8. Spec-vs-handler conformance

**Choice**: Add a small contract test (`pkg/ldapclient/contract_test.go`, build-tagged `//go:build contract`) that boots the real `cmd/server` against an in-memory LDAP fake and runs every SDK method end-to-end. Run on PRs that change either `api/openapi.yaml`, `internal/handler/`, or `pkg/ldapclient/`.

**Why**: Lint catches malformed YAML; codegen-diff catches stale SDK; contract tests catch the spec-vs-reality divergence the other two miss.

**Alternatives considered**:

- *Trust hand authoring*: rejected — proposal explicitly notes that the handler wins over the spec when they disagree, so we need a mechanical check that they agree.

### D9. AGENTS.md is terse

**Choice**: One page, ~80 lines max. Sections: "What this service does", "Auth", "OpenAPI URL", "Calling examples (curl, Go SDK, Go raw)", "Errors". No duplicated schema or endpoint enumeration — point at the spec.

**Why**: Agents are good at fetching and parsing structured documents. The job of AGENTS.md is **discovery**, not duplication. Duplicated content drifts; pointers don't.

**Alternatives considered**:

- *Embed the OpenAPI in AGENTS.md*: bloats the file, makes the spec harder to update.

### D10. Module path strategy

**Choice**: SDK module path is `github.com/<org>/ldap-service/pkg/ldapclient`. While version is `<v1.0.0`, no version suffix in the path. When (and if) we ship 1.0.0, follow standard Go semver: stay at the same path. Add `/v2` only on a true breaking SDK change.

**Why**: Avoids the `/v1` rename treadmill at MVP. Documented clearly so consumers don't get surprised at v2.

## Risks / Trade-offs

- **Risk**: Hand-authored spec drifts silently from handlers between contract-test runs.
  → **Mitigation**: D8's contract test is required on any PR touching handlers, spec, or SDK (CI path filter).

- **Risk**: `oapi-codegen` major version bump produces non-trivial generated diffs, masking real spec changes.
  → **Mitigation**: Pin generator version in `tools.go`. Bumping the generator is its own PR with the diff reviewed in isolation.

- **Risk**: Consumers `go get` the whole `ldap-service` module just to use the SDK, pulling transitive deps from `internal/`.
  → **Mitigation**: Go's `internal/` rule already blocks consumers from importing `internal/`. We additionally minimize `pkg/ldapclient` deps to `net/http` + stdlib. If module size becomes a problem, split to a separate repo (proposal's open question 1, deferred).

- **Risk**: SDK error sentinels become a public API contract — renaming them is a breaking change.
  → **Mitigation**: Document this in `pkg/ldapclient/doc.go`. Keep the initial sentinel set minimal (5 errors); add more only when justified by a real consumer need.

- **Trade-off**: AGENTS.md as-pointer requires agents to do a fetch step (they all can). The trade is single-source-of-truth vs. zero-fetch convenience. We pick truth.

- **Trade-off**: Hand-authoring the spec means we need discipline. We're betting on the contract test (D8) + lint + codegen-diff trifecta to enforce that discipline.

## Migration Plan

This is purely additive — nothing is being deprecated.

**Phase 1 — Land the artifacts:**

1. Author `api/openapi.yaml` covering all 5 endpoints.
2. Add `tools/oapi-codegen-config.yaml` and `tools.go`.
3. Run codegen, hand-author `client.go` / `errors.go` / `doc.go`, write tests.
4. Add Spectral lint + codegen-diff jobs to `ci.yml`.
5. Add `AGENTS.md`.
6. Update `README.md`.

**Phase 2 — Consumer adoption (out of scope for this change):**

- PHP monolith: no SDK migration; reads OpenAPI manually if needed.
- `mfa-service`: starts new integration via SDK (`go get`).
- Future Go consumers: SDK from day one.

**Rollback:**

- Revert the PR. Service continues to work — nothing in `internal/` or `cmd/` changed.

## Open Questions

- **Q1**: Spectral ruleset — default OAS, default + `@stoplight/spectral-owasp`, or a custom ruleset? **Defer**. MVP starts with default OAS; tighten later.
- **Q2**: Do we publish the OpenAPI doc at a runtime endpoint (`GET /openapi.yaml`)? Useful for agents that fetch from the live service. **Defer** — easy follow-up; out of scope here.
- **Q3**: Contract test infra — is there an in-memory LDAP fake usable by `cmd/server` on a `httptest.Server`? Look at `openspec/specs/integration-test-env`. **Resolve during implementation**, not now.
